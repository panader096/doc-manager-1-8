# REFLECTION-harry.md

Reflections for Sprint 3.8 - Intelligent Doc Reviewer (`/harry`), kept separate from `docs/REFLECTION.md` and `docs/REFLECTION-journal.md` per this project's convention.

## Process: brainstorming → spec → plan → subagent-driven implementation

This was the first feature in the project built end-to-end through the full `superpowers` pipeline rather than direct implementation: clarifying questions one at a time before any design (PDF-only, one document per chat, RAG-scale document length, self-reported confidence, hidden self-validation, mandatory-not-optional retrieval, no in-app PDF viewer for v1), then an `ai-architect` dispatch to propose the actual schema/retrieval/validation architecture, a written design doc, a self-reviewed implementation plan with complete code per task, then ten tasks executed with a fresh implementer subagent + independent reviewer per task.

**What the review layer actually caught, before any code ran against a real database:** the reviewer found three real defects in `createChat()`/`deleteChat()` purely by reading diffs — an unchecked `doc_path` update whose silent failure would let `deleteChat()` skip Storage cleanup and permanently orphan a file; `file.arrayBuffer()` called after the row insert with no cleanup path, able to strand a chat at `doc_status='processing'` forever; and, in `HarryChatView.tsx`, a cross-chat state-leakage bug reasoned out purely from React's reconciliation semantics — `HarryChatView` had no `key` prop, so switching chats mid-send could let a slow `sendMessage()` response land in the wrong chat's message list. All three were fixed and re-reviewed clean before ever touching a browser.

**What the review layer could not catch, because it never executes code:** two library/framework integration bugs (below) only surfaced once the app was actually driven in a real browser against the real dev server. This is the concrete argument for why "reviewed clean" and "works" are different claims — the plan's own Task 9 explicitly scheduled a manual smoke run for exactly this reason, and it earned its place in the plan.

## Bug: pdfjs-dist's worker path breaks under Turbopack, in two different ways

`app/lib/harry-ingest.ts` uses `pdfjs-dist` to parse uploaded PDFs. A standalone Node script (`scripts/pdf-parse-demo.mjs`, written during Task 2 specifically to de-risk this) proved extraction worked correctly — but only when run unbundled. Once wired into the real Next.js Server Action and driven through the actual UI, every ingestion failed.

**First failure, from the dev server log:** `Setting up fake worker failed: "Cannot find module '...\.next\dev\server\chunks\ssr\pdf.worker.mjs'"`. pdfjs-dist has no real Worker in Node, so it always falls back to a "fake worker" that dynamically imports its own worker script; in Node it defaults `workerSrc` to the bare relative string `"./pdf.worker.mjs"`, which resolves fine when the module runs unbundled but breaks once Turbopack bundles it into a chunk at a different virtual path.

**First fix attempt, also wrong:** set `GlobalWorkerOptions.workerSrc` explicitly using `import.meta.resolve('pdfjs-dist/legacy/build/pdf.mjs')` — the same pattern already used (defensively, wrapped in try/catch) for a cosmetic font-path warning. This crashed module evaluation entirely: `TypeError: {import.meta}.resolve is not a function`. The font-path code's try/catch had been silently swallowing this exact failure the whole time — the "defensive" wrapping wasn't defending against a hypothetical, it was already firing on every request, just never fatally, so nobody noticed. `import.meta.resolve` is simply not available in this bundled Server Action runtime.

**Second fix attempt, closer but still wrong:** switched both paths to `path.join(process.cwd(), 'node_modules', 'pdfjs-dist', ...)`, since `process.cwd()` is reliably the project root under both `next dev` and `next start`, and doesn't depend on `import.meta` at all. Ingestion then failed a third time, with a much more specific error: `"Only URLs with a scheme in: file, data, and node are supported by the default ESM loader. On Windows, absolute paths must be valid file:// URLs. Received protocol 'c:'"`. Node's dynamic `import()` — which is exactly what pdfjs-dist's fake-worker loader calls internally — rejects a raw Windows path.

**The actual fix:** `pathToFileURL(path.join(...)).href` for `workerSrc` specifically. The font-data path stayed a plain path deliberately — pdfjs reads that one via `fs.readFile` internally, not `import()`, so it never needed the URL conversion; that asymmetry is now called out explicitly in a comment next to both, because two nearly-identical-looking `path.join()` calls, one wrapped in `pathToFileURL` and one not, is exactly the kind of thing a future "cleanup" would silently break.

Each of these three attempts was diagnosed from a real error message in the dev server's own log, not guessed — including restarting the dev server under this session's own control specifically to get log visibility into an already-running instance that predated the session and whose output wasn't otherwise reachable.

## Bug: Next.js Server Actions cap request bodies at 1MB by default

Reported by the actual user, with a real-world PDF attached (a multi-page real estate valuation report with a map, QR codes, and charts). `createChat(title, file)` passes the uploaded `File` straight through the Server Action boundary. Next.js defaults Server Action request bodies to 1MB — a limit that sits well below this app's own, deliberately-chosen `INGEST_MAX_BYTES` (20MB) check, and one that Harry's own code never got a chance to enforce, since the framework rejected the request first.

The dev server log made the actual cause unambiguous: `Error: Body exceeded 1 MB limit.` The fix was one config line (`experimental.serverActions.bodySizeLimit: '25mb'` in `next.config.ts`, deliberately set above the app's own 20MB cap so *that* check is what actually governs the limit, not an arbitrary framework default) — but finding it required reading the server log at all, which the UI gave no reason to do: `HarrySidebar.tsx`'s `handleCreate()` caught every failure mode identically and showed the same fixed string, "Couldn't create the chat — try again," regardless of whether the real cause was a bad file type, an oversized file, an ingestion failure, or this framework-level 413. That error-swallowing was flagged independently by the `ai-code-reviewer` pass on PR #9, before this bug report ever arrived — and then concretely cost real diagnosis time when it did. Fixed afterward: `handleCreate()`, `confirmDelete()`, and `commitRename()` (which had no error handling at all) now surface the actual thrown message.

Verified with a real reproduction, not just reasoning: a synthetic ~2MB file uploaded through the running app confirmed the 413 disappeared and the request reached Harry's own code, which then handled the (deliberately invalid) file content gracefully via its existing error path.

## Bug: conversational memory was built, then thrown away one call later

Reported by the user as a suspicion ("I notice this new functionality does not have memory of the existing chat") rather than an observed error — confirmed by reading the code, then reproduced live before touching anything, in that order.

`sendMessage()`'s draft call correctly replays the full `chat_id`-scoped history, the same full-history-replay mechanism this project uses everywhere memory is needed (`/chat`'s `sendMessage()`, described in `CLAUDE.md`'s AI model calls section). But the value actually shown to the user and written to `reviewer_messages` doesn't come from the draft — it comes from a second, hidden validation call, and that call's message array was built from scratch with only the current question, the draft, and the retrieved document excerpts. No history at all.

Live reproduction before any fix: asked "What is the refund window?" (correct, cited answer), then "Can you repeat exactly what you just told me in your previous answer?" Harry's actual final answer: *"I apologize, but I don't have access to any previous conversation between us. Each conversation with me starts fresh without memory of prior exchanges."* The bug announced itself in its own output.

Fix: `validationConversation` now includes the same history array the draft call used, with one adjustment — sliced to drop its own last entry, since that's the current question, already conveyed via the explicit `"Question: ..."` message that follows; including it twice would just be noise. Re-ran the identical follow-up against the identical chat afterward: *"Here's what I said in my first answer: The refund window is 30 days."*, badge and citation intact.

This is the kind of defect neither a task-level code review nor a passing e2e suite was ever going to catch on its own — the draft call *does* have history, so a reviewer scanning `sendMessage()` for "does this replay history" sees a correct-looking answer at the first call site and has no obvious reason to keep reading into the second one. It surfaced only because the actual, literal user-visible output was read closely enough to notice it was making a specific, checkable claim about itself.

## A quieter thing worth naming: two verification modes, not one

Everything in this file that turned out to be real was found one of exactly two ways: reading a *diff* (the task-level and PR-level reviews — cheap, fast, parallelizable, and it caught genuine defects), or reading a *running system's actual output* (the log lines, the literal text Harry returned). Neither substitutes for the other. The diff reviews are what caught the Storage-orphaning and cross-chat-leakage bugs before they could ever happen in practice. But none of them — not the task reviews, not the PR-level `ai-code-reviewer` pass, not the security scan — could have caught the pdfjs bundling failure, the body-size limit, or the memory bug, because all three are failures of the *actual runtime environment* (Turbopack's bundling, Next.js's own defaults, the literal shape of two API calls in sequence) that only exist once the code is actually executed. The plan's Task 9 scheduled a manual smoke run for exactly this reason, ahead of any bug report ever arriving — and every bug found after merge was found the same way the plan anticipated: by running the thing and reading what it actually said, not by re-reading the code more carefully.
