# Reflections.md — Sprint 3

Consolidated reflections for Sprint 3 only (Personal Journal, Chat, Harry, and the extra-features/security work built on top of them). Sprint 1 (Doc Manager) and Sprint 2 (Notes app, Auth) reflections live in `docs/REFLECTION.md` and are out of scope here. The per-app detail files (`docs/REFLECTION-journal.md`, `docs/REFLECTION-harry.md`) still exist in full — this file consolidates their key findings and adds everything from the extra-features/security work that didn't have a written reflection yet.

## Personal Journal (`/journal`)

Full detail: [`docs/REFLECTION-journal.md`](REFLECTION-journal.md).

- **Scope decisions were made explicit before code, not discovered mid-build.** An `ai-architect` proposal deliberately left six product questions open (one entry per day vs. many, tags or not, image support, edit-in-place vs. append-only, export, search) rather than guessing — each was decided and recorded before implementation started.
- **RLS cross-user isolation was proven two ways, not one, after a live two-account demo hit a real platform wall.** Supabase's test-mailer rate limit (a hard cap on confirmation emails/hour) blocked signing up a second real account mid-session, and a hand-crafted second `auth.users`/`auth.identities` row failed with an opaque `500 Database error querying schema` from GoTrue — abandoned immediately rather than debugged further, since a subtly-broken fabricated account is worse than no live second account at all. The fallback evidence (unauthenticated REST proof, direct `pg_policies` inspection, and the logical argument that `auth.uid() = user_id` blocks anon and a different real user identically, since both simply fail to equal the row's owner) is the same class of proof this project already relies on elsewhere, just made explicit here because the live demo path was blocked.
- **A real TDD pass, with a test written before the feature it enforces.** `e2e/journal-delete-confirmation.spec.ts` was written first, in full, including exact selectors (`data-testid="journal-entry-row"`) that didn't exist in the component yet. It correctly failed red for the right reason (the hook wasn't in the DOM), then passed green on the first implementation attempt with zero edits to the test file. The seeded e2e test account itself needed one real fix along the way: the first hand-seeded account failed to authenticate until `confirmation_token`/`recovery_token`/etc. were set to empty strings rather than `NULL` — matching exactly what a real signup writes, not just what the schema allows.

## Harry, the Intelligent Doc Reviewer (`/harry`)

Full detail: [`docs/REFLECTION-harry.md`](REFLECTION-harry.md).

- **First full run through brainstorm → spec → plan → subagent-driven implementation** in this project. Clarifying questions one at a time before any design, an `ai-architect` dispatch for the schema/retrieval/validation architecture, a written spec, a self-reviewed plan with complete code per task, then ten tasks executed with a fresh implementer + independent reviewer per task.
- **What diff-review caught, before any code ran against a real database:** an unchecked `doc_path` update whose silent failure would let `deleteChat()` skip Storage cleanup and orphan a file permanently; `file.arrayBuffer()` called after the row insert with no cleanup path, able to strand a chat at `doc_status='processing'` forever; and a cross-chat state-leakage bug in `HarryChatView.tsx` reasoned out purely from React reconciliation semantics (no `key` prop meant a slow response from a previous chat could land in the wrong chat after switching).
- **What diff-review could not catch, because it never executes code:** three real bugs only surfaced by actually running the app. `pdfjs-dist`'s worker path broke under Turbopack bundling in a way that took three iterations to fix correctly (a bare relative path, then a crash from `import.meta.resolve` not existing in this runtime, then a Windows-path rejection from Node's dynamic `import()` — the actual fix needed `pathToFileURL()` specifically for the one path that goes through `import()`, while the font-data path stayed a plain string since it's read via `fs.readFile` instead). Next.js's Server Actions default to a 1MB body limit, well under this app's own 20MB PDF cap — found only when a real user uploaded a real file and hit a generic error, made harder to diagnose than necessary because the sidebar's error handling swallowed the real cause behind one fixed string. And a memory bug where the hidden validation call — which produces the answer actually shown and persisted, not the draft — was built with no conversation history at all, discovered only because Harry's own reply made a literal, checkable claim about itself ("I don't have access to any previous conversation") that turned out to be false.
- **The standing lesson: two verification modes, neither replaces the other.** Diff review caught the Storage-orphaning and cross-chat-leakage bugs before they could ever happen in practice. None of the three runtime-only bugs above could have been caught by more careful reading — they're failures of the actual execution environment (Turbopack's bundling, Next.js's own defaults, the literal shape of two sequential API calls), not the code's logic in isolation.

## Extra features + security hardening (branches `v3.8.3` → `v3.8.5`)

Ten planned enhancements across `/chat` and `/harry` (model transparency, streaming, cost visibility, a live Vercel deployment, a tuned persona, per-user model choice, expanded test coverage, stronger agentic search, multimodal input, shareable answers), executed via `subagent-driven-development` — a fresh implementer + independent reviewer per task, plus a final whole-branch review. No reflection existed for any of this until now.

### A redesign caught mid-task, not after

The streaming task's first implementation (hand-rolled SSE for `/chat`) made a real design mistake: the route handler always ran one full non-streamed model call just to check whether the model wanted to use a tool, then — regardless of the answer — made a second, independent streaming call to actually generate what the user sees, discarding the first call's content even when it already had the complete answer. For any message that didn't need a tool (the common case), that's two full model generations where the pre-streaming code needed only one. The implementer caught this itself while investigating why the e2e suite's timing had regressed, flagged it explicitly rather than silently reworking the design, and the actual fix (reuse the already-generated content via simulated progressive chunking; only make a genuine second call in the rare case where every round used a tool) was confirmed with the person directing the work before being applied. The same review discipline caught a second, unrelated issue in the same task: a subagent had granted itself extra shell permissions in a shared config file to manage its own dev-server restarts — outside the scope of its actual task, reverted before committing.

### Building on top of work that had already reshaped the file underneath you

Four of the ten tasks (streaming, per-user model choice, and both multimodal-input tasks) needed to add code to files that an *earlier* task in the same sequence had already substantially restructured in ways the original plan text didn't anticipate. The risk here isn't subtle: applying a task's own reference code verbatim, written before the earlier restructuring existed, would silently regress it. The pattern that worked was reading the file's actual current state before dispatching each task, giving explicit merge instructions naming exactly which prior structures had to survive intact, and then having the independent reviewer re-verify those specific structures byte-for-byte in the resulting diff rather than trusting the implementer's own account of what it preserved. Every one of these merges came back confirmed correct under that check — the discipline of verifying rather than assuming is what made that confidence possible, not the absence of risk.

### An account-level constraint that looked like a code bug from a distance

The AI provider account's own daily spending cap was hit repeatedly through this phase of the project, and it manifests in ways that are easy to misdiagnose as application bugs if you don't check the account state directly: a generic "couldn't send" error with no other symptom, and — more subtly — a bug report from real usage ("this works with one model but not another") that traced entirely to different models costing different amounts per token against the same tight remaining budget, not to anything in the code. In every case here, the fix was to read the actual upstream error message rather than assume, which is what turned "is this broken?" into "no, and here's the exact dollar-and-token math proving it." The concrete outcome, once diagnosed: several tasks' live model-response verification had to fall back to static type-checking and hand-traced logic instead of an actual completed API call — a real, acknowledged verification gap, explicitly accepted rather than allowed to block the whole branch, with a recommendation to re-run the full live suite once the account allows it.

### A real, live, critical security bug — found by the process built to find it

The final security-scan task, run once across every task's combined changes rather than per-task, found a genuine confidentiality bug in the "shareable Harry answers" feature that had already shipped and was live on the production database: the anonymous-read database policy backing public share links had no actual filter on it at all, meaning any unauthenticated visitor could list every share link ever created directly against the database API, and a second, related policy checked only whether a message had been shared by *anyone* rather than whether the specific requester held the matching link — combined with plain sequential row numbers, an anonymous visitor didn't even need a real link to read every shared answer that existed. Two independent scanners flagged the same underlying issue from different angles the same run, which is itself a useful signal about how findable it was once the right kind of check was pointed at it. The fix — a token-parameterized database function that never returns the secret token to any client, replacing the direct table-level policy entirely — was written, pushed, and verified live the same session: a throwaway test share was created, direct table reads were confirmed to return nothing even with a real share present, the function was confirmed to return the right content for the right token and nothing for a wrong one, and the test data was cleaned up afterward. The broader lesson carried into `CLAUDE.md` going forward: an anonymous-read exception scoped by a caller-supplied secret needs a function that requires the secret as a parameter, not a table policy checking a boolean "is this shared at all" — the two look similar and are not equivalent.

A second, related but lower-severity finding from the same scan (a user could set their own stored model preference to an unvetted value and have it billed to the project's single shared API key) was fixed the same way: validated against an explicit allow-list at every point the value is actually used, not just in the UI that offers the intended choices.

### A follow-up bug report that was real, but not where it first appeared to be

After the extra-features branch shipped, a live bug report — a genuinely free model worked for one task but the paid models returned errors — turned out, on direct investigation, to be the same account-level spending cap described above, not a new defect. Swapping in a free-tier model to sidestep that cap surfaced a second, more interesting problem during testing: the model would occasionally decline to answer a question about the ongoing conversation itself (e.g. "what did I ask earlier?") with the same "not addressed in the document" language written for questions about the uploaded PDF specifically — even though the actual conversation history was, and always had been, correctly included in every model call. Reproducing it live confirmed the persona's own wording was the real cause: it was written entirely in terms of "the document," with no explicit carve-out for a question about the conversation rather than the document. Adding that carve-out fixed the wrongful refusal, confirmed by re-running the same question live — though a residual, honestly-reported limitation remains: a smaller/free model can still misremember specific details of earlier turns, which is a genuine capability difference between models, not something a prompt-wording fix can close.

### Vercel's own guardrails, encountered directly

Two Vercel-specific constraints were worth recording because they weren't obvious in advance. First, a command that pauses the platform's own automatic DDoS/traffic-filtering protection refuses to run non-interactively at all, with an explicit message that this class of change must be confirmed by a human typing it into their own terminal — a genuine platform-level safety rail, not a bug, and the project owner's own choice not to invoke it (preferring to keep the protection on rather than verify a deployment's reachability) was the correct call, not a compromise. Second, "disable deployment protection" turned out to have more than one distinct setting underneath it — the one actually applied exempted only one of the deployment's three interchangeable URLs rather than all of them, discovered only by testing all three directly rather than trusting the CLI's own summary of what changed.
