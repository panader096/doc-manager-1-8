# Sprint 3.6 - Chat: AI chat app design

## Summary

A fourth app in the workspace, at `/chat`, called "Sprint 3.6 - Chat". A single, persistent, per-user AI chat conversation backed by the OpenRouter connection set up in `app/lib/ai.ts`. Signed-in only, same pattern as `/notes` and `/journal`.

## Goals

- Scrollable message list, user messages on one side, AI on the other
- Text input at the bottom, send with Enter
- The AI has access to the full prior conversation each turn, so follow-up questions like "tell me more about that" resolve correctly
- The OpenRouter API key never reaches the browser

## Non-goals (out of scope for this pass)

- Multiple conversations / threads — one ongoing conversation per user
- Streaming responses — the full reply is awaited, then rendered
- Editing or deleting individual messages
- Conversation truncation or summarization for very long histories
- Search across chat history

## Data model

New table `chat_messages`:

| Column | Type | Notes |
|---|---|---|
| `id` | bigint identity | primary key |
| `user_id` | uuid | `not null default auth.uid() references auth.users(id)` |
| `role` | text | `'user'` or `'assistant'` |
| `content` | text | message body |
| `created_at` | timestamptz | `default now()` |

RLS: one `for all to authenticated using (auth.uid() = user_id) with check (auth.uid() = user_id)` policy, same pattern as every other user-owned table in this project. No anon access.

Migration: `supabase/migrations/0019_chat_messages_table.sql` — creates the table and RLS policy together (the table is simple enough not to warrant splitting into two files the way the journal migration did).

## Data-access module

`app/lib/chat.ts` is the single source of truth for this app, per CLAUDE.md convention.

```ts
export interface ChatMessage {
  id: number
  role: 'user' | 'assistant'
  content: string
  created_at: string
}
```

- `getMessages(): Promise<ChatMessage[]>` — plain client-side read via `app/lib/supabase/client.ts`, ordered by `created_at` ascending. Same shape as `journal.ts`'s `getEntries()`. Called on page load to hydrate history.

- `sendMessage(content: string): Promise<{ userMessage: ChatMessage; assistantMessage: ChatMessage }>` — a Server Action (inline `'use server'` directive at the top of the function body, same convention as `auth.ts`'s exported actions). Runs entirely server-side:
  1. Get the authenticated user via `app/lib/supabase/server.ts`'s `createClient()` + `getUser()`. If there's no user, throw.
  2. Insert the new user message row.
  3. Load the full prior message history for this user (including the just-inserted message), ordered by `created_at`.
  4. Build the OpenRouter message array: a short system prompt (e.g. "You are a helpful assistant.") followed by the history mapped to `{ role, content }`.
  5. Call `createChatCompletion()` from `app/lib/ai.ts` with that array.
  6. Insert the assistant's reply as a new row.
  7. Return both inserted rows.

This is how conversational memory works: the entire conversation is replayed to the model on every turn. No separate memory/embedding store is needed at this scale.

If step 5 throws (OpenRouter error), the function rethrows after the user message has already been persisted (step 2 already committed) — the user's message is not lost, but there's no assistant reply yet. The client's error handling (below) accounts for this.

## Routing

- `app/chat/layout.tsx` — server component, copies `app/journal/layout.tsx`'s shape: checks `getUser()`, redirects to `/login` if absent, renders a header with a "← Workspace" link, the user's email, and a sign-out form. No sidebar (single conversation, nothing to list).
- `app/chat/page.tsx` — renders `ChatView`.
- `app/lib/supabase/middleware.ts`'s `isProtectedPath` gets `/chat` added alongside `/workspace`, `/notes`, `/journal`.
- `app/workspace/page.tsx`'s `APPS` array gets a new entry: `{ name: 'Sprint 3.6 - Chat', description: 'A simple AI chat that remembers the conversation.', href: '/chat' }`.

## UI

`app/components/ChatView.tsx` (client component):

- On mount, calls `getMessages()` and renders the list in a scrollable container that's flex-1 above the input, auto-scrolling to the bottom whenever the message list grows.
- User messages: right-aligned bubble using `--accent` background.
- Assistant messages: left-aligned bubble using `--bg-modal` background, matching the existing design system (no new tokens).
- A fixed input area at the bottom: a textarea (Enter to send, Shift+Enter for a newline) and a send button, styled consistently with `NoteEditor.tsx`/`JournalEditor.tsx` inputs.
- On submit: appends the user's message to local state immediately with a temporary negative id (optimistic update), clears the input, shows a "thinking…" indicator in place of where the reply will appear, calls `sendMessage(content)`, then on success replaces the temporary message and the indicator with the real `userMessage` and `assistantMessage` (using their real ids) from the response.
- On failure: removes the optimistic message and the indicator, and shows an inline error near the input (e.g. "Couldn't send that — try again"). The user can retype and resend; nothing is left in a stuck or duplicated state.

## Error handling

- No signed-in user in `sendMessage()`: throw; the client treats this like any other failure (shouldn't normally happen since the layout already gates the page).
- OpenRouter request failure (already handled inside `createChatCompletion()` in `ai.ts`, which throws with the response status and body): propagates up through `sendMessage()`, caught client-side, surfaced as the inline error described above.
- Empty/whitespace-only input: the send button is disabled and Enter is a no-op until there's non-whitespace content.

## Testing

Given the project's existing Playwright setup (`e2e/`, signed-in as the seeded test account), a smoke test is reasonable: sign in, navigate to `/chat`, send a message, assert the user message and an assistant reply both appear. Full mocking of OpenRouter isn't attempted here — out of scope for this pass; the test can be added if/when it's worth the setup cost. Not treated as a blocking requirement for this feature.
