# Sprint 3.8 - Extra Features design

## Summary

Ten independent enhancements across `/chat` and `/harry`, plus a Vercel deployment, scoped through a clarifying-question pass (see conversation history — no open questions remain). Organized by the same Easy/Medium/Hard tiers they were requested in. Each item below states its final, confirmed scope; implementation detail lives in the companion plan document(s), not here.

## Easy

### 1a. Model display
Both `/chat` and `/harry` show which OpenRouter model slug produced each assistant message — read from the actual API response (`data.model` in OpenRouter's response body, which reflects what really served the request), not a hardcoded label, so it stays correct if 2c's per-user model choice is exercised. Requires a new column on both message tables (`chat_messages.model`, `reviewer_messages.model`), since the model isn't currently persisted anywhere.

### 1b. Streaming responses
`/chat` only. Harry's two-call flow (draft, then a hidden validation call that produces the answer actually shown) has nothing to safely stream — streaming the draft would show unvalidated content before the self-check runs, which is exactly what that call exists to prevent. `/chat` has a single call with nothing to protect, so it streams naturally.

Implementation: no new npm dependency. OpenRouter's `/chat/completions` endpoint supports `stream: true`, returning Server-Sent Events. `sendMessage()` in `chat-actions.ts` can't return a `ReadableStream` as a Server Action's return value in a way a Client Component can consume token-by-token (Server Action results are a single resolved value, not a stream) — so streaming needs a Route Handler (`app/api/chat/route.ts`) instead, called via `fetch()` from `ChatView.tsx` with a `ReadableStream` reader loop on the client. `sendMessage()`/`chat-actions.ts` stays as the non-streaming path used for anything that isn't the live send (none currently), but the actual live "type and hit send" flow moves to the new route. The user-message insert and the final assistant-message insert (once the stream completes) still go through Supabase exactly as before — only the token delivery mechanism changes.

### 1c. Usage indicator
Token count only (not a dollar estimate), both apps. OpenRouter's response always includes `usage: { prompt_tokens, completion_tokens, total_tokens }` in every response with no extra request parameter needed. Shown as a small inline label under each assistant message (e.g. "342 tokens"). Persisted alongside the model slug (1a) — same new columns' migration adds a `total_tokens` column too, so historical messages keep their real usage figure rather than losing it on reload.

### 1d. OpenRouter privacy settings
Advisory only — no code. Recommendation already given: training toggle off (non-negotiable), Zero Data Retention on if available on the account's plan (Harry processes real, potentially sensitive uploaded documents), otherwise the shortest available retention window. This is an OpenRouter account-level dashboard setting, not something this repo's code can enforce or verify.

## Medium

### 2a. Deploy to Vercel
Uses the existing linked project (`.vercel/project.json`, `projectId: prj_Y1MrqCNfhwh1yNr9RvzWQP4x3HuM`). **`vercel.json` currently has `"git": {"deploymentEnabled": false}`** — automatic git-push deployment is off, so this is a manual Vercel CLI deploy (`vercel --prod`), not something that happens on the next `git push`.

Two blockers found by the Vercel security scanner earlier this project and confirmed still open, both to be fixed as part of this task:
- Deployment Protection (SSO) currently gates the entire deployment, including `/login` — an incognito visit hits Vercel's own SSO wall, not this app's sign-in page. Turn off Deployment Protection (or narrow it so production is public) so the app's own auth is what gates access, matching every other app in this project.
- `OPENROUTER_API_KEY` is entirely absent from Vercel's environment variables (`NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` are already present and correctly scoped). Add it via `vercel env add`, scoped to Production (and Preview, so preview deployments work too) — value copied from `.env.local`, never typed into any file in the repo.

Verification matches the task's own spec: open the deployed URL in a fresh incognito window, confirm it shows the sign-in page and no user data.

### 2b. Tuned persona (Harry only)
Three candidate personas proposed for you to pick from (not built yet — this is a "propose, then you choose, then implement the winner" task, same shape as 2c's model tiers). Candidates, to be refined further once chosen:
1. **Precise & formal** — closer to a real due-diligence reviewer: terse, cites page numbers even more insistently, uses professional register ("Per the document...").
2. **Plain-spoken & direct** — leans into "Harry" as a first-name, approachable colleague reading the document with you: shorter sentences, less hedging, still fully grounded.
3. **Skeptical auditor** — actively looks for what's missing or vague in the document, not just answering what's asked (e.g. volunteers "the document doesn't specify X, which is usually disclosed in reports like this").

`HARRY_SYSTEM_PROMPT` in `harry-actions.ts` is the only thing that changes — no schema, no UI changes. The self-validation prompt (`HARRY_VALIDATION_PROMPT`) stays behavior-focused (checking claims against excerpts) regardless of which persona wins, since validation isn't where personality lives.

### 2c. User-selectable model
Both `/chat` and `/harry`. Three real, current OpenRouter slugs, shown with relative cost framing (not exact per-token pricing, which drifts):
- `anthropic/claude-haiku-4.5` — current default, cheapest/fastest tier
- `anthropic/claude-sonnet-5` — stronger reasoning, ~3-4x the cost
- `google/gemini-2.5-flash` — alternate-provider cheap tier

New `user_settings` table (`user_id` primary key + `chat_model`/`harry_model` text columns, each defaulting to `anthropic/claude-haiku-4.5`), same per-user RLS pattern as every other table in this project. A small settings UI (dropdown) added to both `/chat` and `/harry`'s headers. `sendMessage()` in both `chat-actions.ts` and `harry-actions.ts` reads the user's stored preference and passes it as `createChatCompletion()`'s `model` option instead of relying on `ai.ts`'s hardcoded `DEFAULT_MODEL`.

### 2d. Playwright tests for the AI feature
New signed-out-lockout tests for both `/chat` and `/harry` — confirmed via a repo-wide search that no test anywhere currently verifies "navigate to a protected route while signed out → redirected to `/login`, no data ever rendered." Existing happn-path AI coverage (`e2e/chat.spec.ts`, `e2e/harry.spec.ts`'s test 1) already satisfies that half of 2d and isn't rebuilt.

## Hard

### 3a. Strengthen `/chat`'s agentic search
`/chat` already has model-chosen tool-calling RAG (`search_notes`, a bounded `MAX_TOOL_ROUNDS = 3` loop, query rewriting on weak results) — this is already "agentic RAG" per the task's own definition. Harry's mandatory, automatic retrieval is a deliberate, separate design decision (Harry must never answer ungrounded) and is explicitly out of scope for this item; it does not change.

The enhancement: today, `runSearchNotesTool()` returns whatever chunks `searchNoteChunks()` finds with no visibility into *why* a result might be weak beyond raw similarity score, and the model's only lever for "chain multiple searches for complex questions" is the existing round loop with no structural encouragement to decompose a compound question. Two concrete improvements:
1. The tool result explicitly reports the similarity score band in words ("strong match" / "weak match" / "no match"), not just raw numbers, since the system prompt already asks the model to judge "weak, irrelevant, or empty" results — giving it a legible signal to act on rather than needing to interpret raw floats.
2. `SYSTEM_PROMPT` gains an explicit instruction to decompose a multi-part question into separate `search_notes` calls (one per sub-question) rather than one broad query, within the existing `MAX_TOOL_ROUNDS` budget.

No schema changes. No new tables. This is a prompt + tool-result-formatting change to `chat-actions.ts` only.

### 3b. Multimodal input
Both apps. Images attach to individual messages (not to a whole chat), stored as Storage object references (never base64 in the database), matching every other image-handling pattern in this project (`note-images`, `journal-images`, `profile-photos`).

- **`/chat`**: a new optional image attaches to a single message. Uses the current default model (`anthropic/claude-haiku-4.5`, already vision-capable via OpenRouter) — no new model needed. New `chat_messages.image_path` nullable column, new private `chat-images` bucket, same owner-folder RLS pattern as existing image buckets.
- **`/harry`**: an image can be attached to an individual question within an existing PDF-scoped chat — it's *additional* context for that one question (e.g. a photo of a page, a related document), not a replacement for the chat's PDF grounding. Harry's mandatory-retrieval + hidden-validation flow is unchanged; the image is passed alongside the existing document excerpts and message history in the same `createChatCompletion()` call. New `reviewer_messages.image_path` nullable column, new private `reviewer-images` bucket (kept separate from `reviewer-docs`, which is PDF-only per its bucket's MIME restriction).

`createChatCompletion()` in `ai.ts` needs to accept an optional image (as an OpenAI-compatible `image_url` content part) alongside the existing plain-string message content — this is a real, if contained, change to `ai.ts`'s message shape, used by both apps.

### 3c. Shareable AI outputs
Harry only, one assistant message at a time, text only (no cited excerpts, no source PDF access) — mirrors the existing `/shared/[token]` notes pattern (anon-readable, narrow, explicit exception) rather than inventing a new sharing mechanism. New `reviewer_shares` table (`id`, `message_id` → `reviewer_messages.id`, `share_token` unique text, `created_at`), owner-scoped RLS for the creating user (create/revoke), plus one narrow anon `SELECT`-only policy on `reviewer_shares` joined to the referenced message's plain text content only — no join back to `reviewer_doc_chunks` or `reviewer-docs` Storage from the anon path, so the source document stays private even though one answer derived from it is public. New route `app/harry-shared/[token]/page.tsx` (named distinctly from `/shared/[token]`, which is notes-specific) renders just the shared message's text, no sidebar, no auth, matching `SharedCollectionView.tsx`'s existing read-only shape.

## 4. Security scan
Run once all of the above land, scoped to the changed files only, same `security-scan-changed` process (three scanners in parallel) already used twice this project.

## Global constraints carried into the plan
- Every new table gets the standard owner-scoped RLS policy (`user_id uuid not null default auth.uid() references auth.users(id)`, one `for all to authenticated using (auth.uid() = user_id) with check (auth.uid() = user_id)` policy) — anon access only where 3c explicitly calls for it, and narrowly.
- No new npm dependency anywhere in this plan (1b's streaming is hand-rolled SSE per the confirmed decision).
- `OPENROUTER_API_KEY` stays server-only throughout — 3b's image handling still goes through `ai.ts`'s existing server-only `createChatCompletion()`, never a client-side call.
- Any step that pushes a schema migration to the live Supabase project, or deploys/changes Vercel configuration, is a CHECKPOINT requiring explicit confirmation before it runs — same convention as the Harry build.
