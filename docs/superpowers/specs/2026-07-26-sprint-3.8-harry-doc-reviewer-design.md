# Sprint 3.8 - Intelligent Doc Reviewer ("Harry") design

## Summary

A fifth app in the workspace, at `/harry`, called "Sprint 3 - Intelligent Doc Reviewer". Unlike `/chat` (one persistent conversation per user), this app supports many independent, named chats per user — each chat is scoped to exactly one uploaded PDF, fixed at creation. The assistant persona across every chat is "Harry." Harry answers questions strictly from the chat's document: every claim carries a page citation and a self-rated confidence, and every answer passes through a hidden self-validation call before being shown. Signed-in only, same RLS/auth pattern as `/notes`, `/journal`, and `/chat`.

## Goals

- Two-pane UI (sidebar of chats + selected chat), matching `/notes`'s structure
- One PDF per chat, uploaded at chat creation, never swapped
- Retrieval-grounded answers only — Harry must never answer from general knowledge; if the document doesn't cover a question, Harry says so explicitly
- Per-claim page citation and self-reported confidence (High/Medium/Low), inline in the rendered answer
- A hidden second model call that critiques/revises the draft answer against the same retrieved pages before it's shown or persisted
- Full conversation memory per chat (same full-history-replay mechanism as `/chat`, scoped by `chat_id`)
- Chats can be renamed and deleted; delete removes messages, chunks, and the Storage object
- The OpenRouter API key never reaches the browser

## Non-goals (out of scope for this pass)

- Multiple documents per chat, or swapping a chat's document after creation
- In-app PDF viewer / click-to-jump-to-page — citations are plain text (e.g. "p. 12")
- OCR / scanned or image-only PDFs — rejected at upload with a clear error
- Non-PDF formats (Word, plain text, Markdown)
- Streaming responses
- Editing individual messages
- Search across chats or across a chat's history

## Data model

Three new tables, one new Storage bucket. Same RLS convention as every other user-owned table in this project: `user_id uuid not null default auth.uid() references auth.users(id)`, one `for all to authenticated using (auth.uid() = user_id) with check (auth.uid() = user_id)` policy per table. No anon access anywhere in this app.

**`reviewer_chats`**

| Column | Type | Notes |
|---|---|---|
| `id` | bigint identity | primary key |
| `user_id` | uuid | `not null default auth.uid() references auth.users(id)` |
| `title` | text | user-given chat name |
| `doc_filename` | text | original uploaded filename, shown in the sidebar |
| `doc_path` | text | Storage object path |
| `doc_status` | text | `check (doc_status in ('processing', 'ready', 'failed'))` |
| `doc_status_reason` | text nullable | populated when `doc_status = 'failed'` (e.g. "no extractable text — scanned PDF", "exceeds 100-page limit") |
| `created_at` | timestamptz | `default now()` |

**`reviewer_messages`**

| Column | Type | Notes |
|---|---|---|
| `id` | bigint identity | primary key |
| `user_id` | uuid | `not null default auth.uid() references auth.users(id)` |
| `chat_id` | bigint | `not null references reviewer_chats(id) on delete cascade` |
| `role` | text | `'user'` or `'assistant'` |
| `content` | text | message body (Harry's replies include the inline citation/confidence markers — see UI) |
| `created_at` | timestamptz | `default now()` |

**`reviewer_doc_chunks`**

| Column | Type | Notes |
|---|---|---|
| `id` | bigint identity | primary key |
| `user_id` | uuid | `not null default auth.uid() references auth.users(id)` |
| `chat_id` | bigint | `not null references reviewer_chats(id) on delete cascade` |
| `page` | int | `not null` — the source PDF page this chunk came from |
| `content` | text | chunk text |
| `embedding` | `extensions.vector(1536)` | same model/dimension as the notes pipeline (`openai/text-embedding-3-small`) |

A deliberately separate table from the notes app's `documents` table (migration `0020`) rather than extending it — different owner concept (`chat_id`, not `note_id`), and needs `page`, which `documents` doesn't have. Its own RPC:

```sql
create or replace function match_reviewer_chunks (
  query_embedding extensions.vector(1536),
  match_threshold float,
  match_count int,
  p_user_id uuid,
  p_chat_id bigint
)
returns table (id bigint, page int, content text, similarity float)
language sql stable security invoker
set search_path = public, extensions
as $$
  select
    reviewer_doc_chunks.id,
    reviewer_doc_chunks.page,
    reviewer_doc_chunks.content,
    1 - (reviewer_doc_chunks.embedding <=> query_embedding) as similarity
  from reviewer_doc_chunks
  where reviewer_doc_chunks.user_id = p_user_id
    and reviewer_doc_chunks.chat_id = p_chat_id
    and 1 - (reviewer_doc_chunks.embedding <=> query_embedding) > match_threshold
  order by reviewer_doc_chunks.embedding <=> query_embedding asc
  limit least(match_count, 200);
$$;
```

(`set search_path` included explicitly — migration `0020` shipped without it and failed on push; see that migration's fix commit.)

**Storage**: new private bucket `reviewer-docs`, path `{user_id}/{chat_id}/document.pdf`. Single `for all to authenticated` policy scoped to `(storage.foldername(name))[1] = auth.uid()::text`, same pattern as `note-images`/`journal-images`. No anon read policy — no sharing feature in this app.

**Cascade note**: deleting a `reviewer_chats` row cascades `reviewer_messages` and `reviewer_doc_chunks` via FK. The Storage object is not covered by that cascade — `deleteChat()` must explicitly remove it from `reviewer-docs` in the same action.

Migration: a new numbered file in `supabase/migrations/` (next available number after `0020`), creating all three tables, the RPC, and the bucket + policy together.

## Ingestion pipeline

Runs once, triggered by chat creation:

1. Client: user picks a PDF and names the chat. Client-side check rejects non-PDF and >20MB immediately for fast feedback (not trusted as the real guard).
2. Server Action `createChat(title, file)`:
   - Inserts `reviewer_chats` with `doc_status = 'processing'`.
   - Uploads the file to `reviewer-docs/{user_id}/{chat_id}/document.pdf`.
   - Parses the PDF server-side with `pdfjs-dist` (new dependency — approved), page by page, via `getTextContent()`.
   - **Guards**: reject (set `doc_status = 'failed'`) if page count exceeds 100 or file exceeds 20MB; reject if no page yields extractable text (scanned/image-only PDF — no OCR in v1).
   - Each page's text is split into chunks via the existing `chunkText()` (`app/lib/chunking.ts`), tagged with its page number, embedded via `createEmbeddings()` (`app/lib/ai.ts`), and inserted into `reviewer_doc_chunks`.
   - On success, `doc_status = 'ready'`.
3. The sidebar reflects `doc_status`: a processing indicator while ingesting (can take a while for ~100pp), a failed state with `doc_status_reason` if rejected, normal once ready. The chat is not usable for questions until `ready`.

## Chat answer pipeline

Retrieval here is **mandatory and automatic**, not a model-chosen tool call (unlike `/chat`'s optional `search_notes`) — Harry must never skip grounding:

1. User sends a message → inserted into `reviewer_messages`.
2. Server embeds the message and calls `match_reviewer_chunks()`, scoped to `p_user_id` and this `chat_id`, for the top 5 relevant page chunks above a 0.3 cosine-similarity floor — same starting defaults (`MATCH_COUNT`/`MATCH_THRESHOLD`) as `searchNoteChunks()` in `embeddings-actions.ts`, not empirically tuned yet.
3. **Draft call**: full message history for this chat + the retrieved chunks (each labeled with its page number) → `createChatCompletion()`. System prompt establishes the Harry persona and the hard rule: answer only from the provided excerpts; if they don't cover the question, say so explicitly rather than answering from general knowledge. The model is instructed to mark each claim with its page and a self-rated confidence using a plain-text convention:

   ```
   Harry can process refunds within 30 days [p. 12, confidence: High].
   ```

   (No JSON-mode is used anywhere in this project; parsing this marker format must stay tolerant — an unparseable or missing marker renders as plain text rather than breaking the message.)
4. **Validation call (hidden)**: the draft plus the same retrieved chunks go back to the model with an instruction to verify every claim is actually supported by those specific pages, revising wording, downgrading confidence, or dropping unsupported claims. Only this final answer is shown and persisted — the draft and the critique call are ephemeral, same pattern as `/chat`'s tool-loop round-trips.
5. If retrieval returns nothing relevant, the draft step is instructed to say so directly rather than reach for general knowledge.

## Data-access modules

Following the `/chat` two-file `'use server'` convention (forced by Next.js — inline Server Actions can't live in a plain file imported by a Client Component):

- **`app/lib/harry.ts`** — client-safe reads: `getChats(): Promise<ReviewerChat[]>`, `getMessages(chatId): Promise<ReviewerMessage[]>`. Canonical `ReviewerChat` / `ReviewerMessage` interfaces live here.
- **`app/lib/harry-actions.ts`** (`'use server'`) — `createChat(title, file)` (runs the ingestion pipeline above), `sendMessage(chatId, content)` (runs the answer pipeline above), `renameChat(chatId, title)`, `deleteChat(chatId)` (removes the Storage object, then the row — table cascade handles messages/chunks).
- **`app/lib/harry-ingest.ts`** — the PDF parse/chunk/embed logic, kept separate from `harry-actions.ts` since it's substantial enough to warrant its own module; imported by `createChat()`.

## Routing

- `app/harry/layout.tsx` — server component, same shape as `journal/layout.tsx`/`chat/layout.tsx`: `getUser()` check, redirect to `/login` if absent, header with "← Workspace" link, user email, sign-out.
- `app/harry/page.tsx` — empty state / "select or create a chat" prompt, matching `/notes` and `/journal` home behavior.
- `app/harry/[id]/page.tsx` — the selected chat.
- `app/lib/supabase/middleware.ts`'s `isProtectedPath` gets `/harry` added alongside `/workspace`, `/notes`, `/journal`, `/chat`.
- `app/workspace/page.tsx`'s `APPS` array gets a new entry: `{ name: 'Sprint 3 - Intelligent Doc Reviewer', description: 'Upload a document and ask Harry expert questions about it, with page citations and confidence scores.', href: '/harry' }`.

## UI

- **`HarrySidebar.tsx`** (client component) — lists the user's chats (title, `doc_filename`, status badge if not `ready`), a "New chat" control opening a name + PDF-upload form, modeled on `NotesSidebar.tsx`. Rename/delete affordances per chat, with a delete confirmation (matching the pattern in `JournalSidebar.tsx`'s `confirmingDeleteId`).
- **`HarryChatView.tsx`** (client component) — on mount, calls `getMessages(chatId)`; scrollable message list, user messages right-aligned (`--accent`), Harry's left-aligned (`--bg-modal`), matching `ChatView.tsx`. Harry's replies are rendered by parsing the `[p. N, confidence: X]` markers out of `content` and displaying each claim with an inline page/confidence badge; unparseable text renders as-is. Input area (textarea, Enter to send, Shift+Enter newline) pinned to the bottom, disabled while `doc_status !== 'ready'`.
- Optimistic send + reconcile-by-id, same as `ChatView.tsx`'s `handleSend()`.

## Error handling

- Upload: non-PDF or >20MB rejected client-side (fast feedback) and re-validated server-side (not trusted from the client).
- Ingestion failure (page cap, size cap, no extractable text): `doc_status = 'failed'` with `doc_status_reason`, surfaced in the sidebar; chat remains listed (not silently dropped) so the user knows what happened and can delete/retry.
- Draft or validation call failure (OpenRouter/network error): the user's message is already persisted; an inline error is shown in the chat (same spirit as `/chat`'s existing load-error handling) rather than losing the message.
- No signed-in user in any Server Action: throw — shouldn't normally happen since the layout already gates the page.
- Delete: Storage object removal is attempted before the row delete; if Storage removal fails, the action surfaces an error rather than leaving the row deleted with an orphaned file (avoids silent orphaning).

## Testing

Playwright, `e2e/`, signed in as the seeded test account, not run in CI (real OpenRouter + embedding calls, same as the existing chat RAG tests):

- **Happy path**: create a chat with a small seeded test PDF, ask a question it answers, assert the reply contains a page citation and a confidence marker.
- **Grounding**: ask something the test PDF doesn't cover, assert Harry says so rather than answering from general knowledge (mirrors `chat-notes-rag.spec.ts`'s honest not-found case).
- **Management**: rename a chat, delete a chat, assert it disappears from the sidebar and its messages/chunks are gone.

## Open implementation notes

- Ingest caps (100 pages / 20MB) are a starting judgment call, not user-specified numbers — revisit if real usage hits them often.
- The self-validation pass roughly doubles per-turn latency/cost (draft + critique calls); accepted for v1 as the cost of a genuine second check rather than a single self-check-instruction call.
- Confidence scores are the model's self-assessment, not a statistically grounded metric — the validation pass mitigates but doesn't guarantee accuracy; this is a known limitation, not a bug to fix later.
